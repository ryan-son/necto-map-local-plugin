# Map Local 사용법

[English](usage.md)

패널의 각 부분이 하는 일과, 앱이 규칙으로 무엇을 하는지 설명해요. 자주 하는 일의 짧은 단계는
[recipes-ko.md](recipes-ko.md)를 보세요. 무언가 동작하지 않으면
[troubleshooting-ko.md](troubleshooting-ko.md)에서 증상을 찾으세요. 패키지 설정은
[README](../README-ko.md)에, 배포 빌드에서 Map Local을 빼는 방법은
[release-builds-ko.md](release-builds-ko.md)에 있어요.

## 규칙이 적용되는 방식

앱 코드는 두 줄이에요. 플러그인을 등록하고 Necto를 시작해요. 허용 호스트·규칙·응답·지연·
오류는 모두 패널에서 정해요. 패널에서 바꾼 내용은 즉시 앱에 저장되고, 다음 요청부터 적용돼요.

마지막 설정은 앱에 저장돼요. **Map Local이 켜져 있으면 Necto Mac 앱을 닫아 둔 동안에도
규칙이 적용돼요.** 앱을 다시 실행했을 때의 첫 요청부터 적용돼요. Map Local이 켜져 있고 앱에
영향을 주는 동안 앱에 [배지](#배지)가 보여요. 배지를 누르면 Map Local을 끌 수 있어요.

기본으로는 어떤 규칙도 응답하지 않는 요청이 실서버로 가요. 이 동작은
[규칙 없는 요청](#규칙-없는-요청)에서 바꿀 수 있어요. 허용 호스트가 없으면 Map Local은
아무것도 목업하지 않아요.

### 플러그인은 한 번만 등록하기

Necto는 같은 ID(`io.github.ryan-son.maplocal`)의 두 번째 플러그인을 모든 빌드에서 거부하고,
Debug 빌드에서는 assert로 멈춰요. 실행 중에 플러그인을 바꿔 등록하려면 먼저
`NectoSDK.unregister(id: "io.github.ryan-son.maplocal")`를 부르세요.

플러그인을 다시 만들어도 문제는 없지만 아무것도 바뀌지 않아요. Map Local은 엔진(요청마다
무엇을 받을지 정하는 코드)과 설정, [앱 코드에서 차단한 호스트](#허용-호스트)를 앱 프로세스마다
한 번만 준비해요. 나중에 만든 `NectoMapLocalPlugin(blockedHosts:)`는 처음 것의 `blockedHosts`를
그대로 써요.

## 허용 호스트

Map Local은 허용 호스트로 가는 요청만 목업해요.

- **허용 호스트가 없으면 Map Local은 아무것도 목업하지 않아요.** 호스트를 추가하려면 패널 맨
  위의 「+ 호스트」 칸에 호스트나 URL을 입력하거나 붙여 넣고 Return을 눌러요. 「트래픽」 탭에서
  요청을 목업해도 그 호스트가 추가돼요.
- **국제화 도메인 이름(IDN)은 punycode로 적어요.** 앱 요청의 유니코드 호스트는 엔진에 퍼센트
  인코딩된 채 오므로 `한국.kr`로 허용하면 어떤 요청과도 맞지 않아요. 「+ 호스트」 칸은 이런
  호스트를 추가하지 않고 「유니코드 호스트는 punycode(xn--…)로 입력하세요」라고 알려요.
  `한국.kr`이라면 `xn--3e0b707e.kr`로 입력하세요.
- **운영 서버 호스트는 앱 코드에 적어 목업되지 않게 해요.**
  `NectoMapLocalPlugin(blockedHosts: ["api.example.com"])`로 넣은 호스트는 허용 호스트여도
  절대 목업되지 않아요. 스킴·포트·대소문자는 무시하고, 패널에서는 이 목록을 바꿀 수 없어요.
  이 문서에서는 이 호스트를 「앱 코드에서 차단한 호스트」라고 불러요. **이 목록은 요청을 막지
  않아요.** 요청은 그대로 실서버로 가요. 운영 서버를 목업하지 못하게 할 뿐, 요청이 운영 서버에
  닿는 것은 막지 않아요.

## 규칙 없는 요청

패널의 「규칙 없는 요청」에서, 허용 호스트로 가면서 맞는 규칙이 없는 요청이 무엇을 받을지
정해요. 다른 호스트와 앱 코드에서 차단한 호스트로 가는 요청은 항상 실서버로 가요.

- 「실서버로 보내기」(기본값): 그 요청은 실서버로 가요.
- 「차단(421)」: 그 요청은 421을 받아요. 규칙 없는 요청이 목업 토큰을 실어 실서버로 가면
  401이나 강제 로그아웃이 날 수 있는데, 차단(421)이 이를 막아요. 인증을 목업할 때 권해요
  ([인증 규칙](#인증-규칙) 참고).
- 「인터넷 연결 없음 (-1009)」, 「연결 끊김 (-1005)」, 「시간 초과 (-1001)」: 서버에 닿을 수
  없는 것처럼 그 `URLError`로 실패해요. 요청에 맞는 규칙은 여전히 응답하니, 함께 실패해야
  하는 규칙은 꺼 두세요. 「시간 초과」여도 요청은 바로 실패해요. 늦게 실패하게 하려면 규칙의
  응답에서 「네트워크 오류」를 그 오류로 정하고 「지연(ms)」을 주세요. 기기 자체의 네트워크
  상태(`NWPathMonitor`)는 바뀌지 않아요.

## 규칙 매칭

다음이 모두 맞아야 규칙이 요청에 응답해요.

- **메서드.** 요청의 HTTP 메서드가 규칙의 메서드와 같아야 해요.
- **호스트.** 요청의 호스트가 규칙의 호스트와 같아야 해요. 호스트를 비운 규칙은 허용 호스트
  전체와 맞아요. 어느 쪽이든 요청의 호스트가 [허용 호스트](#허용-호스트)여야 해요.
- **경로.** `{id}` 같은 세그먼트는 비어 있지 않은 아무 세그먼트 하나와 맞아요. 경로는 앱이
  보내는 대로 퍼센트 인코딩해서 적어요. 공백 대신 `%20`이에요.
- **쿼리 조건.** 아래를 보세요.

### 쿼리 조건

쿼리 조건은 편집기의 「쿼리 조건」에 적는 키=값 줄이에요. 적은 키가 모두 정확히 그 값으로 있을
때 맞아요. 적지 않은 키는 보지 않아요. 값은 퍼센트 인코딩을 푼 글과 비교해요. `+`는 공백으로
바꾸지 않고 `+` 그대로 비교해요. 조건이 없으면 「모든 쿼리」예요.

규칙 목록은 조건을 `GET /api/sites ?page=2`처럼 보여 줘요. 그래서 같은 경로의 규칙을 쉽게
구분할 수 있어요.

트래픽에서 만든 규칙에는 쿼리 조건이 없어요. 「이 쿼리일 때만」을 켜면 그 요청의 쿼리를
조건으로 옮겨요. 이미 맞는 규칙이 있으면 패널이 그 규칙에 응답을 추가하므로, 「이 쿼리일
때만」 체크 상자가 보이지 않아요.

### 여러 규칙이 맞을 때

쿼리 조건이 더 많은 규칙이 응답해요. 같으면 목록에서 위에 있는 규칙이 응답해요.
켜진 규칙 두 개가 같은 요청에 맞을 수 있으면, 각 규칙의 편집기에서 쿼리 조건 아래에 그 요청에
어느 규칙이 응답하는지 나와요. 둘보다 앞서는 세 번째 규칙이 있으면 대신 그 규칙을 알려 줘요.

## 트래픽 탭

패널은 「규칙」과 「트래픽」 두 탭이에요. Necto의 언어 설정(한국어·영어)을 따라요.

「트래픽」 탭은 앱의 요청을 엔드포인트별(「엔드포인트」) 또는 시간순(「시간순」)으로 보여 주고,
요청마다 결과를 표시해요. 상태, 결과(「목업」·「실서버」·「차단」·「확인 불가」),
「허용 호스트만」으로 거를 수 있어요. 검색칸은 메서드·호스트·경로와 앱이 보낸 쿼리
문자열까지 찾아요(`page=2`, `siteId=101`).

「시간순」 보기에서 고른 요청은 새 요청이 위에 쌓여도 제자리에 있어요. 목록 위 줄이 쌓인 수를
세요. 「최신 보기」를 누르면 가장 최근 요청으로 이동하고, 「일시정지」를 누르면 목록이 멈춰요.

요청을 고르면 응답이 보이고, 거기서 규칙을 만들어요.

1. 「이 응답으로 목업」을 눌러요. 응답을 볼 수 없으면(예:
   [Necto 네트워크 플러그인](#실제-응답-캡처하기)이 없을 때) 패널은 대신 「빈 응답으로 목업」을,
   그 요청과 맞는 규칙이 이미 있으면 「규칙 열기」를 보여 줘요.
   목업하면 그 요청의 호스트도 허용 호스트에 추가돼요. 버튼 아래 줄이 그렇게 알려 줘요.
2. 「규칙」 탭에서 응답을 고쳐요.

앱에서 결과를 확인하는 단계까지 모두 담은 절차는
[recipes-ko.md](recipes-ko.md#화면을-다른-데이터로-보기)에 있어요.

맞는 규칙이 있는데 목업되지 않은 요청이면, 트래픽 상세가 그 이유를 한 줄로 알려 줘요. 이유별
해결 방법은 [troubleshooting-ko.md](troubleshooting-ko.md#요청이-목업되지-않은-이유)에 있어요.

요청을 목업한 규칙이 그 요청의 쿼리 키를 모두 보지는 않는다면, 「규칙 열기」 옆의 「이 쿼리
전용 규칙」을 누르세요. 그 요청의 쿼리를 조건으로 한 규칙을 만들 수 있어요. 새 규칙은 앱이
지금 받는 응답으로 시작해요.

트래픽에서 쿼리 조건과 함께 만든 규칙은, 그 규칙이 처음 응답할 때까지 패널이 지켜봐요. 그
사이에 경로는 맞는데 쿼리 때문에 응답하지 못한 요청이 오면, 트래픽 상세가 어느 조건 때문인지와
해결 버튼을 보여 줘요.

### 실제 응답 캡처하기

실제 응답(상태·헤더·본문)을 보고 새 규칙에 채우려면 Necto 네트워크 플러그인을 Map Local
**다음에** 등록하세요.

```swift
#if DEBUG
import NectoURLSessionCapture   // URLSessionNetworkPlugin은 이 모듈에 있어요
#endif

#if DEBUG
NectoSDK.register(NectoMapLocalPlugin())      // 먼저
NectoSDK.register(URLSessionNetworkPlugin())  // 나중에
NectoSDK.start()
#endif
```

순서가 중요해요. Necto 0.2.0에서 직접 확인한 결과예요.

- Map Local을 먼저 등록하면 목업된 요청이 목업 응답과 함께 「트래픽」 탭에 보여요. 요청마다 한
  번씩만 기록돼요.
- 네트워크 플러그인을 먼저 등록하면 목업된 요청이 「트래픽」 탭에서 사라지고, 실서버로 간
  요청이 두 번 기록돼요. 목업된 요청이 Necto 기록에 보이지 않거나 실서버로 간
  요청이 두 번 기록되면 패널이 경고를 띄워요.
- 네트워크 플러그인이 없어도 탭은 요청을 보여 주지만 응답은 볼 수 없어요. 요청으로 규칙을
  만들면 빈 200 JSON 응답이 돼요.

대가가 있어요. 네트워크 플러그인은 요청을 `URLSession(configuration: .ephemeral)`로 다시
보내요. 그래서 이 요청은 앱 세션의 delegate(인증 챌린지·피닝), 공용 쿠키, URLCache를 거치지
않아요. 캡처는 선택 기능이에요.

이 기능은 Necto 문서에 없는 동작에 기대요. 패널은 다른 플러그인의 브리지, 곧 네트워크
플러그인의 `necto.device.network-records.*`를 불러요. Necto 0.2.0은 이를 연결해 주지만,
Necto의 브리지 문서는 앱 브리지를 한 플러그인 범위로 설명해요. 패널은 연결할 때마다 사용 가능
여부를 확인하고, 기록을 쓸 수 없으면 Necto가 준 이유를 보여 줘요. 「규칙」 탭은 기록 없이도
동작해요. 이 동작은 이후 Necto 릴리스에서 바뀔 수 있어요.

## 인증 규칙

로그인이나 토큰 요청에 응답하는 규칙에는 「인증 규칙」(「로그인·토큰을 내주는 응답입니다」)을
켜 두세요.

그런 규칙이 응답한 뒤에는 앱이 목업 토큰을 들고 있을 수 있어요. 이 문서에서는 이것을
*목업 세션*이라고 불러요. Map Local은 앱을 다시 실행해도 목업 세션을 기억하고, 앱에서
로그아웃한 뒤 패널에서 「로그아웃했습니다」를 누를 때까지 남겨 둬요. 목업 세션이 남아 있을 수
있는 동안에는 다음과 같아요.

- Map Local이 켜져 있으면 앱 배지에 `Map Local 🔑`가 떠요. Map Local을 끄면 배지는
  사라지지만 목업 세션은 남아 있어요.
- 패널에 「로그아웃했습니다」 버튼이 있는 알림이 보여요.
- 인증 규칙을 끄거나 지울 때 패널이 앱에서 먼저 로그아웃하라고 안내해요. 켜진 인증 규칙이
  허용 호스트에 응답하는 동안 Map Local을 끄거나 그 호스트를 지울 때도 같아요.

규칙 없는 요청이 목업 토큰을 실서버로 들고 가지 않게 하려면
[규칙 없는 요청](#규칙-없는-요청)도 「차단(421)」으로 정하세요.

## 배지

Map Local이 켜져 있고 다음 중 하나가 적용되는 동안 앱에 작은 `Map Local` 배지가 보여요.

- 켜진 규칙이 허용 호스트로 가는 요청에 응답할 때
- 「규칙 없는 요청」이 「차단(421)」이나 오류로 되어 있고, 허용 호스트가 있을 때
- [목업 세션](#인증-규칙)이 남아 있을 수 있을 때

이 중 아무것도 적용되지 않거나 Map Local이 꺼져 있으면 앱은 아무것도 보여 주지 않아요.

배지는 화면 아래 홈 인디케이터 오른쪽 옆에 있어요. 홈 버튼이 있는 기기에서는 상태 막대에
있어요. 그곳에서는 보이기만 하고 눌리지 않을 수 있으니, 그런 기기에서는 패널에서 Map Local을 끄세요. 배지 자리만 터치를 받고, 나머지 터치는 모두 앱으로 가요. 키보드가 올라온 동안에는
숨어요. VoiceOver는 버튼으로 읽어요.

### 앱에서 Map Local 끄기

배지를 누르면 적용 중인 것을 보여 주는 시트가 열려요. 응답 중인 규칙 수, 그중 최대 3개의 이름
(패널과 같은 이름), 규칙 없는 요청이 무엇을 받는지, 목업 세션이 남아 있을 수 있는지를 보여
줘요. 시트의 「Map Local 끄기」는 패널의 「Map Local 켜짐」 스위치와 같은 설정을 쓰므로 패널도
따라 바뀌어요. 목업 세션이 실서버로 갈 수 있으면 시트가 앱에서 먼저 로그아웃하라고 안내해요.

시트는 기기 언어를 따라요. 기기가 한국어를 우선하면 한국어, 아니면 영어로 보여요.

## 되돌리기와 키보드

규칙이나 응답을 지울 때 먼저 묻지 않아요. 대신 「되돌리기」를 보여 줘요.

Necto가 ⌘Z(편집 메뉴의 실행 취소)와 Esc를 먼저 가져가므로, 이 키는 패널에 오지 않아요.
그래서 되돌리기·닫기·지우기에는 늘 보이는 버튼(「되돌리기」, ×, ⓧ)이 있어요.

패널에서 쓰는 키예요. ↑↓, Return, ⌘↩, `/`는 Necto 0.2.0에서 실측했어요.

| 키 | 동작 |
| --- | --- |
| ↑ ↓ | 목록에서 이동 |
| Return | 상세의 주 동작으로 포커스 이동 |
| ⌘↩ | 「이 응답으로 목업」(버튼에 단축키가 보여요) |
| `/` | 검색 |
| ← → | 분할 손잡이에서 목록 폭 조절(두 번 누르면 기본 폭) |

## 패널이 볼 수 있는 것

- **패키지를 링크하는 것이 곧 권한이에요.** Necto는 디바이스 플러그인에 설치 확인 창을 띄우지
  않아요. 앱에 패키지를 넣으면 그 패널이 플러그인의 디바이스 브리지 전체에 접근해요
  ([Necto: bridges](https://github.com/toss/necto/blob/main/docs/bridges.md)). 설정을 읽고
  바꾸고, 토큰을 포함한 모든 요청 기록을 봐요. 직접 관리하는 빌드에만 넣으세요.
- **내보내기와 캡처는 값을 가리지 않아요.** 「설정 복사」, 트래픽 캡처, 요청 기록은 토큰·쿠키·
  비밀번호를 가리지 않고 원래 값 그대로 실어요. Necto 네트워크 기록과 같아요.
- **복사할 때 경고하지만 값은 바꾸지 않아요.** 복사한 설정에 다음 중 하나가 있으면 패널이 한
  줄로 경고해요.
  - JSON 웹 토큰(JWT) 모양 값
  - `auth` 태그가 붙은 규칙(인증 규칙)
  - 응답 헤더 Authorization·Cookie·Set-Cookie의 값
  - 이름에 `token`·`secret`·`password`·`apikey`(`api-key`, `api_key` 포함)·`session`이
    들어간(대소문자 무관) 응답 헤더·쿼리 조건 키·본문 JSON 키의, 비어 있지 않은 문자열이나 숫자 값

  공유하거나 커밋하기 전에 확인하세요.

## 알려진 한계

iOS 26.4 시뮬레이터와 Necto 0.2.0에서 실측했어요.

- **`NectoSDK.register`보다 먼저 만든 세션과 먼저 읽은 세션 설정(`URLSessionConfiguration`)은
  가로채지 않아요.** 등록하면 Map Local이 `URLSession.shared` 앞에 들어가고, 그 뒤에 읽는
  모든 `URLSessionConfiguration.default`·`.ephemeral` 세션 설정의 `protocolClasses` 맨 앞에도
  들어가요. 그 전에 읽은 세션 설정의 `protocolClasses`에는 Map Local이 없어요. 그 세션 설정으로 만든 세션도 마찬가지예요. `URLSession.shared`는 먼저 썼어도
  가로채요. 등록은 `App.init`이나 `application(_:willFinishLaunchingWithOptions:)`처럼 앱
  시작의 가장 이른 시점에 두세요.
- **`protocolClasses`를 통째로 바꾼 세션 설정에서는 Map Local이 빠져요.** 일부 SDK처럼
  `config.protocolClasses = [MyProtocol.self]`로 쓰면 Map Local이 들어 있던 목록이 사라져요.
  기존 목록 앞이나 뒤에 붙이는 것은 괜찮아요. 되살리려면 목록을 정한 뒤 맨 앞에
  `NectoMapLocalPlugin.protocolClass`를 넣으세요.

  ```swift
  #if DEBUG
  config.protocolClasses = [NectoMapLocalPlugin.protocolClass] + (config.protocolClasses ?? [])
  #endif
  ```

  `protocolClass`를 넣은 세션 설정으로 만든 세션은, 그 설정을 언제 만들었든 플러그인을
  등록하기 전이어도 Map Local이 가로채요. 등록보다 먼저 만들어야 하는 세션도 이 방법으로
  가로챌 수 있어요.
- **`URLSession` 위에 만든 라이브러리(예: Alamofire, Moya)에도 같은 두 가지가 필요해요.** 그
  라이브러리가 세션을 만들기 전에 Map Local을 등록하세요. 라이브러리가 `protocolClasses`를
  통째로 바꾼다면 맨 앞에 `NectoMapLocalPlugin.protocolClass`를 넣으세요. Alamofire `AF` 같은
  공유 세션은 처음 쓰는 순간 만들어져요. 등록 전에 어떤 코드든 `AF`를 쓰면, 그 세션은 등록 전에
  만든 세션이 되어 가로채지 않아요.
- **백그라운드 세션은 가로채지 않아요.** `URLSessionConfiguration.background(withIdentifier:)`의
  전송은 앱 밖의 시스템 프로세스에서 돌고, 그 프로세스는 앱의 `URLProtocol`을 보지 않아요.
  Debug 빌드에서는 포그라운드 세션을 쓰거나, 전송을 외부 목업 서버로 보내세요.
- **`WKWebView`는 가로채지 않아요.** 페이지 로드, `fetch`, `XMLHttpRequest` 모두요. WebKit은
  별도 프로세스에서 직접 통신해요.
- **목업 3xx는 따라가지 않고 그대로 돌려줘요.** 앱은 `Location` 헤더가 붙은 3xx를 받고, 그
  목적지는 요청되지 않아요. **실제** 리다이렉트의 목적지가 규칙과 맞으면 그 홉은 목업돼요.
  첫 요청에는 서버가, 리다이렉트된 요청에는 규칙이 응답해요.
- 요청이 쿠키를 다루면(`httpShouldHandleCookies`, 기본값 켜짐) 목업 응답의 `Set-Cookie`는 세션의
  쿠키 저장소가 아니라 **항상 `HTTPCookieStorage.shared`**에 들어가요. Map Local이 세션의 쿠키 저장소에 쓸 수 있는 공개 API가 없어요. ephemeral 세션이나
  별도 쿠키 저장소를 쓰는 세션이라면 목업 쿠키가 그 세션에 반영되지 않고 공용 저장소에 남아요.
  목업 쿠키는 Map Local을 끈 뒤에도 공용 저장소에 남아, 공용 저장소를 쓰는 세션의 실제 요청에
  실릴 수 있어요.
- 목업 응답을 쓰는 동안에는 서버의 API 계약(요청·응답 형식)이 바뀌어도 앱에서 드러나지 않아요.
  계약이 바뀌었는지는 다른 도구로 확인하세요.
